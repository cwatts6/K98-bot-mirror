## Observation contract and proportionality

Classify each operation by its actual effects, not a method name such as inspect or verify:

1. **Passive presentation:** render existing status/evidence. Opening a report or status
   view must not initiate producer work, provider probes, refreshes or recovery actions.
2. **Background observation:** bounded discovery/readback. It must yield to useful work,
   avoid acquiring business ownership or locks that block producers, and release its own
   resources before deferral. Its persistence/logging must not extend business transactions.
3. **Active verification:** an intentional probe or action-boundary validation. Identify its
   side effects, necessity and scheduling explicitly; never disguise it as a passive read.
4. **Recovery execution:** an authorised or policy-approved mutation. It retains the
   appropriate ownership checks and is separate from merely observing the operation.

For each retained check record: the concrete failure it prevents; consumer of its result;
facts that can change; earliest/latest useful validation point; frequency; SQL/CPU/IO and
provider costs; resources/locks acquired; cleanup; retry eligibility; and operator action.
Disposition is keep, simplify, consolidate, automate, remove, or investigate, with evidence.
One check at a real ownership boundary may be essential; repeating stable checks at every
layer requires separate justification. Dirty reads are not an automatic simplification.

The target is that observation never causes a producer failure, deadlock, stranded claim
or false failure incident. Qualification must demonstrate this in supported overlapping
workloads and failure scenarios, including implicit SQL read locks and observer bookkeeping.
Shared resource cost must be measured and bounded with a justified budget before design
approval. Finite tests cannot prove zero cost or every possible interleaving; uncovered
paths stay explicitly unqualified rather than being described as harmless.

| Situation | Intended handling |
|---|---|
| Brief contention or an inconsequential delay followed by success | Automatic handling; aggregate diagnostic timing if useful; zero operator actions. |
| Busy background read | Defer and recheck with bounded backoff; never declare business failure from observer unavailability. |
| Completed work with stale workflow status | Reconcile existing authoritative completion automatically; no producer replay. |
| Verifiably finished operation with a retained reservation | Automatic exact cleanup where a reviewed policy permits it; identify SQL lock versus durable reservation versus stale incident status. |
| Persistent loss of monitoring or materially blocked delivery | One deduplicated incident stating impact, evidence, automatic handling attempted and useful next action. |
| Genuinely uncertain mutation or a decision to discard/repeat work | Preserve the restriction and explain the specific unresolved evidence or operator decision. A click is not a substitute for missing evidence. |

Set thresholds by operation impact, expected duration and progress, not one arbitrary global
delay. Silence must not conceal stuck work or indefinitely unavailable monitoring. Resolved
failures remain historical without requiring acknowledgement; ordinary polls are not failures.
