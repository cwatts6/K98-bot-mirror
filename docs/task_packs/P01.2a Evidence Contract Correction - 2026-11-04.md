# P01.2a evidence contract correction

Status: implementation authorized on 4 November 2026. Local work precedes PR
readiness; this is not a deployment or production-acceptance receipt.

## Scope and responsibility

Correct the evidence contract as one group: known startup actor/origin, malformed
verification versus no checker, visible failed event construction, unknown-stage
counts, current versus historical loss and eviction provenance, and compatibility
with the actual deployed readers. Preserve business APIs, mandatory receipts,
physical drain, first failures, parent/child identities, authorization and passivity.
No SQL, provider protocol, command registration or dependency changes are intended.

P05 owns the later repository-wide reliability confirmation: refresh Bot and SQL
source pins and the caller/action census, perform a separate entrypoint/sink sweep,
and map all A01-A14/D01-D06 obligations to implementation, executable assertions
and production evidence. Include manual/scheduled/legacy/fallback/restart paths,
combined failures, compatibility and cost. Earlier packages must deliver their own
complete evidence contract first. This gate is required, not started, and does not
authorize a whole-codebase security scan or replay of accepted production work.

## Regression and acceptance gates

| ID | Requirement and required proof |
| --- | --- |
| R1 | Establish startup provenance before scope entry. Preserve it through children, threads, deadlines, cancellation and settlement. Concurrent unrelated callers remain unknown; collection requester is never substituted. |
| R2 | Separate no checker, pending checker, malformed output, verifier failure and valid completion. Unknown has a bounded reason and code-owned verifier provenance. Never inspect or stringify arbitrary result objects. |
| R3 | Fault event identity/time/encoding/offer after successful context allocation. Execute business work once and preserve its result/error; expose bounded nonrecursive loss accounting. If loss reporting itself fails, record the explicit observability limit. |
| R4 | Unknown stages are counted without exporting arbitrary labels. Restore and export retain counters without duplication. |
| R5 | Export historical and current-process counters separately. Bounded eviction evidence identifies reason, observation time, cutoff and incarnation; unavailable historical detail stays unknown. |
| R6 | Exercise frozen original V1 and deployed V2 readers through upgrade, downgrade and re-upgrade. Declare any reduced compatibility view explicitly and preserve original first failure. Do not infer compatibility by changing both reader and writer in one test. |

Before implementation, retain failing regressions against the deployed baseline.
Trace each requirement through producer, validation, persistence/restore and both
report forms. Keep actual shared MGE/event/default-owner tests and the combined
long-worker/report-deadline/monitor-failure/cancellation case. Requalify producer
cost and bounds for changed diagnostic code, then run full-suite, smoke/command,
architecture/deferred/security-routing, lint and updater-transition checks on the
final candidate. Security review is Changes, Deep off, on the exact final diff.
Historical successful runs remain evidence for their source pins only.

Eviction summaries retain at most four reason keys. Each count spans the available
retained history; its timestamp, cutoff and incarnation describe the latest
recorded eviction for that reason, not every counted event. The history-availability
flag remains false when older detail was unavailable or rejected. Current versus
historical aggregate counters are exported separately; a missing historic counter
is unknown rather than an invented zero. This is bounded evidence, not an unbounded
per-eviction audit stream.

The verification reason vocabulary distinguishes no checker, pending, not reached,
cancelled checker, failed checker, malformed result, incomplete evidence,
unsupported stage, unavailable projection and verified outcome. Consumed fields
inside a returned dictionary are type-checked before comparison; unrelated payload
objects remain uninspected. These distinctions do not replace domain receipts.

## Compatibility design checkpoint

The deployed V2 reader accepts only the unknown actor enum. Adding a new enum is
not transparently compatible with that reader. Resolve and test the persistence
representation and the rollback coverage contract before publishing any candidate;
retain immutable earlier updater transitions and qualify the new source pair.
The selected downgrade contract is the existing separately published V1-compatible
view: the frozen deployed V2 reader rejects extended typed rows, counts the
rejection, and restores their V1 copies as explicit legacy projections. The
original first failure survives. Actor and verification extensions are not retained
by that old writer; re-upgrade must label those historical rows and unavailable
counter detail as unknown. This is a deliberately reduced downgrade view, not
transparent bidirectional V2 compatibility. It does not authorize replay. The
frozen-reader regression covers this actual behavior rather than assuming it.

No readiness or deployment claim is made while the remaining qualification gates
are open. If preserving the new attribution detail through downgrade becomes a
deployment requirement, the release must instead keep an explicitly preserved
new-format artifact and qualify that separate deployment procedure before use.
