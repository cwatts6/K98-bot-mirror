## Alternatives and value

| Option | Benefit / cost | Decision |
| --- | --- | --- |
| Do nothing | No implementation cost; every ordinary display can still create provider/SQL work and misleading freshness. | Reject: source-confirmed F11 remains. |
| Change only the command | Small diff; leaves button and scheduled card active, plus journal locking. | Reject: same root cause remains in equivalent callers. |
| Periodic probes or new collector | Could supply newer general signals; introduces producer cost, ownership and failure paths without demonstrated need. | Reject for P01.3; P02 owns any later justified probe policy. |
| Retained observations, common projection/rendering, remove automatic log scans | Eliminates health-triggered SQL/provider work and journal locking with small service/UI changes; can truthfully show unknown for long periods. | Recommended. |

Value is removal of unnecessary work and improved interpretation, not an increased count of healthy indicators. No measured latency saving or incident reduction is claimed before qualification. The loss of generic error-spike notices is explicit; independent recovery notifications and explicit log inspection are not replacements for every possible log-only fault.

## Concrete architecture and data contract

### Ownership and APIs

Use `services/operator_status_service.py` as the small plain-data assembler (`snapshot(now_utc, now_monotonic)`); keep SQL execution imports inside the active `check_sql` path so importing presentation does not load the execution stack. `services/gsheets_health_service.py` owns its probe snapshot. Keep `check_sql`, `check_health` and `HealthProbe.observe` as explicitly documented active compatibility APIs; no UI calls them. No new active entrypoint is enabled.

Add `HealthProbe.snapshot()` which reads fixed retained records only. It cannot consume a task result, clear `_task`, invoke a callback, schedule work or await completion. The existing owner records start/completion in its execution path, including late completion with no remaining UI observer. Retain at most latest completion and latest failure per existing SQL/Sheets owner, plus current execution metadata. Fixed assignments and bounded classification are best effort: optional metadata failure must not change original return/exception or physical ownership.

A request has a process-local sequence/reference and an internal scope binding. Sheets scope distinguishes the actual configured target; SQL scope identifies the existing connection purpose. Do not disclose raw destinations, account identifiers, credentials or arbitrary exception text. A concurrent active caller for a different scope must not relabel the original task/result; return an unavailable/mismatched-scope observation without replacement work. Selection of a different configured target invalidates relevance, not ownership. Existing same-scope callers still share the task.

The assembler reads only already-loaded source modules/owners; missing initialization is unknown, never an import/bootstrap/refresh fallback. Reuse the existing loaded-source pattern in `services/recovery_evidence_bundle.py`, without invoking its archive builder. Existing owners publish a small immutable presentation record at their normal state transitions. Readers capture one published reference per source, without acquiring any lock, including a nonblocking lock attempt. Never assemble a supposedly coherent record by reading several independently changing fields. Qualify reference publication and immutability on the supported runtime; do not assume safety from unrelated dictionary operations. Preserve existing writer synchronization, business/report getter defaults and physical ownership. No additional writer lock, worker, timer or observer is introduced. Optional bounded publication failure must preserve business results and retain the previous record with its original timestamp.

While a source owner is busy, readers use its previous published record; if none exists, show unavailable/unknown. Busy or unavailable presentation is not a failure or a reason to alert. The existing five-minute dashboard update reads again; manual Refresh can read sooner. Do not schedule a per-reader recheck, spin, poll, queue a retry or start a provider probe. Records are coherent per source, not a transactionally simultaneous whole-system snapshot; retain each source's own provenance.

For startup, expose a narrow selected-field snapshot from the existing `_steps` owner, rather than copying arbitrary completion dictionaries. Select at most four known relevant steps, primitive feature outcome, observer/physical state, reference and observed time. Do not run verification again or infer a provider success from a parent/child Boolean. Optional-source errors affect that component only.

Extract `HealthView` and one card builder to `ui/views/health_view.py`; pass callbacks or values into it rather than importing the bot singleton. Commands and bot lifecycle code remain thin. Reuse existing interaction acknowledgement, redaction and embed validation. No generic dashboard framework or service dependency on Discord objects.

### Record shape and state rules

Proposed plain versioned projection: `health_observations_v1`, captured UTC, process-local scope, and fixed component keys. Each component carries `source`, safe `scope_label`, `observed_utc`, `age_seconds`, `freshness`, `execution`, `outcome`, bounded `reason`, and optional reference. Source-observation time is never substituted with capture/render time. Missing values have a reason, not fabricated defaults.

| Dimension / case | Display rule |
| --- | --- |
| No observation, restart, invalid shape/time or irrelevant scope | Unknown; do not assert an operation is running. |
| Actual owned unfinished task | In progress, start/elapsed if known. An observation deadline or 300-second stall annotation is not a settled provider failure. |
| Completion success | Last observed success for the named check/scope; never all systems operational or permission to write. |
| Completion failure | Degraded for that observation; preserve last failure independently of later success and show whether current relevance is stale. |
| Deferred admission / no provider entry | Unavailable/deferred observation, not provider failure; no automatic retry from the UI. |
| Stale evidence | Show last outcome and age with current state unestablished. Never refresh to satisfy the freshness label. |
| Source update in progress / reader failure | Use the previous immutable published record with original time, or unavailable if absent. Reader failure affects only that component. No lock acquisition, new retry or alert. |
| Shutdown | Presentation marked shutting down; no new probe admission; existing work retains its owner. |

Agreed provider display freshness threshold: 60 minutes, explicitly a presentation heuristic, not a health guarantee, polling interval, expiry of ownership or alert deadline. Crossing it alone never alerts or initiates work. Keep recovery's existing source-specific 90-second freshness and progress semantics: this measures the age of a successful recovery-monitor cycle, whose loop waits 30 seconds between completed cycles; advancing work can remain progressing with older completed evidence. Crossing 90 seconds alone does not send an alert or prove provider failure. Label monitor activity separately from provider observations. Startup/cache results are historical activity with their own timestamps and source age; do not renew provider freshness from them. Use monotonic time for current-process elapsed durations and UTC for displayed provenance. Invalid/future/incomparable timestamps yield unknown age; never silently make them fresh.

The card headline is `Retained observations` with component status, not `All systems operational`. Neutral/amber covers unknown/stale/in-progress; an observed failure remains visibly degraded with its date. Discord connectivity is a distinct local observation. Show `Rendered at` separately from evidence dates. Refresh means redisplay retained information. Footer points to the existing explicit `/ops logs` flow and explains that the five-minute cadence updates the card, not provider checks.

Unknown, stale-only, busy, deferred and in-progress observations do not become provider-failure alerts. No probe is started to decide whether to alert. Existing independent recovery alerts remain untouched; P04 owns further escalation/history policy.

- Reserve a provider-alert observation key before attempting its DM. Mark acknowledged only on success; an unknown/failed delivery remains attempted/unconfirmed and is not resent by the next render. ### One interpretation, existing notification routes

Source-confirmed routing: the pinned health card is posted to `STATUS_CHANNEL_ID` and its scheduler can DM `ADMIN_USER_ID`; `/ops dl_bot_status` separately renders status and offers recovery-centre access; recovery incidents and monitor-outage messages use `NOTIFY_CHANNEL_ID`. The existing health DM has reason text but no dashboard link. These source facts do not establish live channel IDs or whether those channels coincide.

Use the common projection/state rules for the health card and command, preserving per-source timestamps and visibility. An actionable health DM should identify impact/action and link to the existing dashboard message when its identity is known; absent identity is not a reason to create a card from the notification path. Incident alerts retain their existing recovery owner and action entry. Use navigation links to the appropriate existing channel/message rather than moving recovery callbacks onto a channel where their authorization rejects them. Preserve admin-only recovery actions and evidence visibility; never widen permissions to make navigation work. No new notification route or independent failure classifier per surface. Qualification must compare equivalent evidence across both views and verify safe navigation for different status/notification channel IDs.

Narrow lifecycle corrections stop/settle the dashboard at teardown, prevent reconnect restart during teardown and retain message identity on transient fetch failure. They are not an outage detector. A stopped bot or stopped dashboard loop cannot reliably announce its own failure; the operator accepts user reports for rare whole-bot outages and requests no new detector. Preserve existing meaningful delivery-failure reporting without treating stale observation age as an outage. P04's notification/monitoring-loss work must carry this accepted whole-bot limitation forward.

## Exact boundary for side-effect claims

`snapshot()` and projection/render building must perform zero SQL/provider/authority/recovery calls, zero filesystem access, zero task/thread/process creation, zero lock acquisition (including try-locks), and no writes to business state. Callback tests intercept the active entrypoints and journal reader even on cache miss. Intended Discord sends/edits, view registration and existing message identity bookkeeping are adapter effects, tested separately.

Existing command usage telemetry remains outside the pure health-data path: the decorated command logs its normal event, which can produce JSONL and later batch SQL writes. Existing denial audit and operational logging also remain. Do not hide these effects behind a zero-I/O claim or disable mandatory audit. Qualification records baseline/candidate telemetry counts and failure behavior separately, requiring no amplification or new dependency. P01.3 guarantees no health-triggered SQL/Sheets probes or business/recovery execution; it does not certify all logging infrastructure as nonblocking. If unchanged telemetry prevents the agreed end-to-end cost/non-interference gate, stop and scope that dependency explicitly rather than exempting a measured failure.
